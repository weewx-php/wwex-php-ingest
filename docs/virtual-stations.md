# Virtual stations

Use a virtual station for a WeeWX service that adds measurements to LOOP packets.
Each instance has its own process, service configuration, station UUID and queue.
It appears as a separate station for adoption and field mapping in PHP.

The virtual driver generates only `dateTime` and `usUnits`. Services add the
observations before serialization. Packets with no measurements (including only
null or excluded values) are skipped. No weather values are simulated.

## PurpleAir

1. Install [weewx-purple](https://github.com/chaunceygardiner/weewx-purple) using
   the [extension installation procedure](operations.md#installing-drivers-from-github).
   Add `requests>=2.32` and `python-dateutil>=2.9` to the root-owned
   `/etc/weewx-php-ingest/requirements.txt`, one per line. Install them into the
   active environment:

   ```sh
   sudo /opt/weewx-php-ingest/current/.venv/bin/python -m pip install -r /etc/weewx-php-ingest/requirements.txt
   ```

   Future collector releases reinstall this requirements file automatically.
2. Run `sudo weewx-php-ingest configure` and select **Virtual**.
3. Set `loop_interval` (seconds) and `unit_system` (default `METRICWX`). Leave
   advanced settings off. Select **PurpleAir** as the service and enter
   the sensor hostname/IP and port (normally `80`).
4. Setup tests a service-enriched reading. Add another station to configure another
   sensor, or finish and adopt the new station in PHP.

The collector includes the virtual driver; the PurpleAir extension is installed
separately and remains unmodified. No additional physical weather station is needed.

For manual configuration, see [two independent PurpleAir stations](../examples/weewx-virtual.conf).
Keep the collector ID and token generated by installation. Each instance uses its
own `Purple.Sensor1` and `Ingest.Services` sections. A physical station and virtual
stations may share the same collector configuration.

PurpleAir is polled through its local HTTP `/json` endpoint; uploads to PHP still
use verified HTTPS. The tested upstream service emits `pm1_0`, `pm2_5`, `pm10_0`,
`pm2_5_aqi` and `pm2_5_aqi_color`. It applies its own PM2.5 correction and freshness
policy. PHP already knows the concentration fields; define custom measurement
semantics for AQI fields before using them in archives. Python XTypes and
accumulator definitions are not transferred to PHP.

## AirGradient, Davis AirLink and air-Q

Install the corresponding WeeWX extension separately, add its Python requirements
to `/etc/weewx-php-ingest/requirements.txt`, and install them in the active venv
using the command above. Run `configure`, select **Virtual**, then select the
service name. Add one virtual station per device.

| Profile | Extension | Python requirements | Setup |
|---|---|---|---|
| AirGradient | [weewx-airgradient](https://github.com/chaunceygardiner/weewx-airgradient) | `requests`, `python-dateutil` | Host and port; default field mapping added if empty |
| AirLink | [weewx-airlink](https://github.com/chaunceygardiner/weewx-airlink) | `requests`, `python-dateutil` | Host and port |
| air-Q | [weewx-airQ](https://github.com/roe-dl/weewx-airQ) | `pycryptodomex`, `six` | Host (optionally `:port`) and hidden password prompt; units service added automatically |

AirGradient uses `/measures/current`; AirLink uses `/v1/current_conditions`.
air-Q uses `/config` and AES-encrypted `/data` responses. Its device must support
this API (the tested upstream service specifies the Science option). The password
remains in the protected `weewx.conf`, separate from the upload token.

The [three-device example](../examples/weewx-air-quality.conf) shows the generated
configuration structure. For air-Q, the normal unprefixed names can be reused in
every virtual instance because each has its own identity and process.

### Field semantics

- AirGradient maps PM and CO2 to `pm1_0`, `pm2_5`, `pm10_0` and `co2`. It retains
  `tvocIndex`, `tvocRaw`, `noxIndex` and `noxRaw` under distinct names. The indices
  and raw sensor values are not gas concentrations. Existing custom `LoopFields`
  mappings are preserved.
- AirLink supplies instantaneous PM, one-minute averages, available nowcasts and
  numeric AQI fields. Keep these separate when mapping them to PHP; they are not
  independent instantaneous measurements to add together.
- air-Q supplies standard PM/CO2 fields and device-specific fields such as
  `airqTemp`, `airqHumidity`, `airqPressure`, `noise` and `TVOC`. In `METRICWX`,
  temperature is Celsius, pressure is mbar, noise is dB and `TVOC` is converted
  from the sensor's ppb to WeeWX's ppm. Additional gas mass/fraction fields need
  explicit measurement definitions in PHP.

The air-Q profile excludes `airqDeviceID`, `airqStatus` and `airqBattery` because
the upstream service can put text in them. It also excludes upstream `no2`:
that service defines it as a gas fraction, whereas PHP's standard `no2` means
mass concentration. Use `no2_m` with an explicit µg/m³ definition instead. These
exclusions follow the device prefix if configured. Sensor faults are handled by
the upstream service and remain visible in its local logs.

No reports, local archive database or proxy-history backfill are enabled by these
profiles. Polling, calibration, freshness checks and device-specific limitations
remain those of the installed upstream version. In particular, the tested air-Q
service does not enforce a wall-clock age bound on received sensor records.

## Other services

Configure installed service classes under the instance's `Ingest.Services` and
their normal settings alongside `Station` and `Virtual`. The assistant accepts a
comma-separated list of data service classes; configure other groups and
service-specific options in `weewx.conf`.

`Virtual.loop_interval` accepts 0.1–60 seconds (default 10).
`Virtual.unit_system` accepts `US`, `METRIC` or `METRICWX`. Services must emit values
in the packet's declared unit system. Each tick uses a fresh packet; any caching,
freshness checks and polling cadence belong to the service.

Virtual stations use software archive generation only. They do not read hardware
history or send local aggregates. PHP builds archives from the transmitted LOOP
observations. Services requiring a physical console, a local archive database or
report generation need separate integration.

With no service readings, status shows `waiting_for_service`. Empty ticks do not
reset the measurement watchdog; prolonged silence triggers the normal worker
restart policy. Adjust the instance's startup/silence timeouts for slow services.

## Verification

`tests/test_virtual.py` runs the original PurpleAir 7.2 service from a pinned,
checksum-verified [upstream fixture](../tests/fixtures/purple_upstream/README.md).
Two local HTTP sensor simulators exercise separate worker processes, stale-data
recovery, empty packets, station identity, guided setup and hardware probes.

With `WEEWX_PHP_ROOT` and PHP/SQLite available, the tests also verify both stations'
adoption through the real PHP receiver, HTTPS delivery, exact field preservation,
and duplicate-safe retry after a lost acknowledgement. No physical PurpleAir
device is required by the tests.

`tests/test_service_profiles.py` additionally runs unmodified AirGradient 4.0,
AirLink 4.1 and air-Q 0.9b3 against pairs of simulated local APIs. air-Q responses
are encrypted with the test password. Tests check separate identities/fields,
invalid-data rejection by the probe, numeric field handling and real PHP adoption
and journal storage when the PHP integration environment is available. Physical
devices and other upstream versions have not been verified by these tests.
